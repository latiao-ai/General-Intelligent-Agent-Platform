# 模型请求与恢复策略

整体机制与当前回归结果见 [智能体中台运行机制说明](../智能体中台运行机制说明.md)。平台准入与修订约束见 [业务平台接入约束](platform-guardrails.md)。

## 规划失败不会自动执行业务

初次规划只负责提出计划。模型没有返回有效计划时，不拼固定的搜索/生成/发布链，也不生成一段普通回答来替代用户要求的业务变化。

- 网络连接错误、429 和 5xx 在请求次数与总运行时间预算内有限重试；结构化调用默认最多两次真实请求。
- 每次真实发送单独计数。SDK 内置重试关闭，聊天作答也进入请求计数。
- 硬超时不重试。服务端 Retry-After 超过允许等待时间时，停止本次调用，不能提前重发。
- 401/403 等配置和认证拒绝不重试。给用户安全说明，不暴露 provider 原始错误中的密钥或内部地址。
- 结构化输出不合法时，带格式修复要求重试，原目标和约束仍然保留。
- 计划的工具、参数或目标约束校验失败，最多修复一次；仍失败进入 waiting_input，不执行残缺计划。初次规划与收到补充后的修订遵守同一条：修订的第一版不合法时，把「上一版调整 + 结构化校验错误」交回模型修一次，第二轮仍不合法才停在等人。
- 模型故障或无法生成结构化结果进入 interrupted；保存运行和错误类别，允许恢复同一 run。
- 完整请求超限进入 waiting_input；保留要求和已有结果，调整要求或配置后继续。

初次规划还没成功、也没有任何动作时，resume 可以重新规划。已有动作却找不到计划，仍禁止重新规划冒充恢复。有旧计划的修订失败时保留计划供审计，但不继续派发已过时的剩余步骤。

执行前审查同时接收候选工具的输入 schema、输出 schema、完整描述和服务端字段规则。操作前现场是摘要，省略字段不代表工具不会返回该字段。对后续读取的引用应按输出合同校验，并在运行时绑定真实回执；合同明确不支持的路径仍拒绝，缺少输出声明本身不作为“字段不存在”的证据。

修订只提交剩余步骤，但保留原目标的完成条件。已经成功执行的动作，可通过原步骤编号、工具公开名称或稳定工具键匹配已有证据；即使新的片段不再包含该工具，也不应报 `criterion_target_unknown`。未执行或失败的旧动作不能作为已完成证据，也不能为消除校验错误而重复已成功的写入。

本地只读回答的模型故障或预算拦截不会自动补偿此前已成功的业务修改。写请求结果未知仍按既有待核实规则处理。

## 需要观察或用户确认的阶段计划

规划器可以将依赖查询结果、平台确认或异步回执的任务拆成片段。准备片段使用
`after_segment=observe`，并在 `observation_goal` 中明确要核对的字段、等待的确认和后续目标。
独立计划审查同时接收片段策略、观察目标和完成条件，核对本片段是否适合执行；
不能因准备片段尚未产出最终结果而强迫规划器越过确认。普通 `verify` 计划仍须覆盖完整要求。

准备片段仍须有真实工具步骤，写入后仍需读取核对。执行后按真实回执观察，缺少必要确认时等待批准，
不能把方案登记成功当作最终完成。确认后重新读取平台状态，已经提交的任务只跟踪和验收，避免重复提交。
原目标与最终结果验收保留，不因采用阶段计划而放宽授权或完成条件。

平台回传已受理任务号时，通过原运行的补充输入继续，只查询已有任务，不再次提交。
观察阶段的外部确认等待可以在收到补充后重新规划；存在待审批的中台动作授权时，
仍须使用原审批入口，补充文字不能消费或替代审批。会话已有目标的 409 回执包含
`after_event_id`，接入方续跑同一任务时从该游标之后订阅，避免旧结束事件提前关闭新一轮进度。

## 完整请求的统一门禁

所有 structured_call 与 chat_reply 都在发送前调用 context.prepare_request。覆盖初始规划、校验修复、用户修订、观察决策、最终作答和记忆摘要；每次重试都重新检查。

核算材料包括完整 system（含画像和规则）、全部消息、模型绑定的工具参数 schema、消息包装与工具调用包装。实际输出上限与预留输出保持一致。

可用输入额度：

```text
min(LLM_INPUT_BUDGET,
    LLM_CONTEXT_WINDOW - LLM_OUTPUT_TOKENS - LLM_CONTEXT_MARGIN)
```

输入使用 UTF-8 字节上界保守估算，未使用联网分词器。该估算通常明显大于真实 token 数，以安全余量换取较低的有效容量；并非服务商的精确计费 token。部署时必须按实际模型窗口配置，不能把默认值当成模型能力声明。

原有 1800/2200 等用途预算用于历史选择，与这次完整请求的总门禁分开。旧装配器也会按所有板块合计报告超限。

## 超限时如何处理

先移除较早的可选历史，保留当前请求及 system/developer 规则。结构化输入还可移除旧会话摘要，但保留明确关键事实；结果摘要只有带完整证据引用时才能省略，状态与引用保留。

每次省略都写入模型可见的上下文预算说明，禁止模型把省略内容当成已经阅读。没有完整引用的证据不裁剪。当前输入、补充要求、权限、业务落点、完成条件、工具定义均不静默截断。仍然超限就拒绝发送，不消耗模型请求预算。

初次规划和收到补充后的修订共用工具选择：从完整授权目录选择本次相关工具，
只将选中的完整参数定义放入模型请求，避免续跑重新载入整个目录。
选择不会扩大权限，候选步骤仍按完整授权目录和已有动作账本校验；不按固定前 24 项截取。
选中目录仍超限时明确提示缩小范围。旧 REVISION_CATALOG_LIMIT 配置已移除。

## 报告与配置

每次预检生成 context_budget 事件；图执行中的事件会持久化，图外摘要调用仍有服务端日志。报告仅记录用途、各部分大小、预留量、裁剪种类和是否超限，不包含提示词正文或密钥。

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| LLM_CONTEXT_WINDOW | 32768 | 部署方声明的模型上下文窗口 |
| LLM_INPUT_BUDGET | 24576 | 完整输入的保守估算上限 |
| LLM_OUTPUT_TOKENS | 4096 | 预留并实际限制的最大输出 |
| LLM_CONTEXT_MARGIN | 2048 | 工具协议与分词差异的安全余量 |
| LLM_RETRY_MAX_DELAY | 2 | 短暂重试的最大等待秒数，最高 30 |

修改环境配置需要重启进程。超限时应缩小材料或选用并正确配置更大窗口的模型，不能通过任意提高窗口数值绕过模型本身的限制。

## 回归验证

测试使用真实 PostgreSQL 验证初次规划失败后恢复同一运行、零动作零模型发送的预算拦截，以及回答失败不撤销已成功的修改。模型与 HTTP 故障为受控替身，不连接真实模型或业务平台。
