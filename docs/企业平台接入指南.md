# 企业平台接入指南

版本：1.1  
更新日期：2026-10-28  
适用版本：`webpage-agent-main` 当前代码  
读者：企业平台接入负责人及研发同事

企业平台接入中台，主要准备四样东西：**登录票签发能力、运行现场上下文、MCP Server、调用凭据与授权范围**。本文按这四项展开，字段、样例和配置都归入对应项，便于直接分工。

| 企业提供的四项 | 解决的问题 | 最小交付内容 |
| --- | --- | --- |
| 1. 登录票签发能力 | 当前用户是谁、属于哪家企业 | 后端签票能力、身份标识、公钥及签发说明 |
| 2. 运行现场上下文 | 用户正在操作哪个项目、哪个对象 | 当前项目／对象引用及后端签名证明；不依赖现场时可暂不接入 |
| 3. MCP Server | 中台能调用企业的哪些业务能力 | 可连通的服务地址、首批工具及参数／结果说明 |
| 4. 调用凭据与授权范围 | 中台代表谁调用、允许做到什么范围 | 调用令牌、所属企业／用户、工具及资源权限说明 |

先围绕一个双方确认的业务场景打通这四项，再逐步扩展工具和权限。企业已有的接口文档、字段表或测试环境可以直接复用，不要求为每个细项另写一份材料。异步、取消、产物下载等说明，只在首批场景涉及相应能力时补充。

企业平台继续持有业务数据和业务权限，中台负责理解目标、规划、调用和记录结果。企业无需交付业务平台源码或用户密码。示例中的名称、地址和编号均为占位示例。

## 1. 登录票签发能力

### 1.1 企业准备什么

企业后端基于已有登录态，为当前用户签发一张短时登录票，并提供验签公钥和必要的身份字段说明。公钥、企业编号和用户编号都属于这一项的配套信息。

| 细分内容 | 提供方式 |
| --- | --- |
| 后端签票能力 | 可联调的签票接口及说明；接口路径由企业决定 |
| 身份标识 | 企业 `tenant_id`、平台 `platform_id`、稳定用户 `sub` 和身份源编号 |
| 验签信息 | `issuer`、RSA 公钥 PEM、`kid`；私钥由企业保管 |
| 联调样例 | 一个测试用户及其签发的短时票，据此验证兑换流程 |


### 1.2 登记信息

企业提供下列信息，由中台方写入可信接入配置：

| 字段 | 要求 |
| --- | --- |
| `connection_id` | 双方约定的稳定接入编号 |
| `issuer` | 签发方标识，与票据 `iss` 精确匹配 |
| `identity_provider_id` | 稳定身份源编号；多个平台确实共用账号体系时才共用 |
| `allowed_tenants` | 允许该签发方声明的企业名单 |
| `allowed_platforms` | 允许该签发方声明的平台名单 |
| `kid` 与公钥 | RSA 公钥 PEM 及对应版本标识；轮换时提前登记新公钥 |
| `audience` | 登录票为 `agent-hub-login` |

当前只支持 RS256，公钥来自中台登记配置；不根据票据中的地址自动拉取公钥，也不提供自动 JWKS 轮换。

### 1.3 登录票格式

JWT 头部：

```json
{"alg":"RS256","typ":"agent-login+jwt","kid":"enterprise-key-v1"}
```

JWT 载荷结构示例，时间字段需在每次签发时生成：

```json
{
  "iss": "https://identity.enterprise.example",
  "aud": "agent-hub-login",
  "sub": "employee-10001",
  "tenant_id": "enterprise-a",
  "platform_id": "business-platform-a",
  "iat": 1793145600,
  "exp": 1793145660,
  "jti": "unique-ticket-id-for-each-login",
  "name": "示例用户"
}
```

`iss`、`aud`、`sub`、`tenant_id`、`platform_id`、`iat`、`exp`、`jti` 必填；`name`、`email` 可选。`iat` 和 `exp` 是整数秒时间戳。按当前默认配置，有效期不超过 60 秒，允许约 5 秒时钟误差；双方联调时核对部署值。票据不超过 8 KB。

`sub` 使用稳定用户编号，不使用可变的姓名或邮箱。同一签发方的同一 `jti` 只能兑换成功一次；失败重试若票已消费，应重新签票。票据中的 `role` 不能直接授予中台权限，权限映射由中台登记。

### 1.4 登录流程

1. 用户先登录企业平台。
2. 企业后端验证当前登录态，并为该用户签票。
3. 企业前端将票提交给中台 `POST /api/auth/exchange`：

```json
{"ticket":"<企业后端签发的JWT>"}
```

4. 中台返回会话 Cookie，默认名称 `agent_session`。之后由浏览器携带 Cookie 调用中台。
5. 调用 `GET /api/me` 核对身份；退出调用 `DELETE /api/auth/session`。

默认会话时长为 7200 秒，可由部署配置调整。续期采用新票重新兑换。企业平台退出登录时，应同时处理当前中台会话退出；企业账号停用与全部中台会话的自动联动撤销需另行确定，不能假定已经打通。

| 兑换返回码 | 企业前端处理 |
| --- | --- |
| 200 | 会话建立，继续进入助手 |
| 400 | 检查请求结构及中台是否启用票据模式 |
| 401 | 检查票据、登记、公钥及时间；必要时重新签票 |
| 409 | 票已兑换，重新获取新票；不要循环提交旧票 |
| 503 | 中台仓储未就绪，按约定稍后重试 |

## 2. 运行现场上下文

### 2.1 企业准备什么

这一项用于理解「当前项目」「选中的对象」。企业提供简短的现场信息，并由后端确认后签名。不依赖页面现场、由用户明确指定业务对象的首批场景，可以暂不接入；对象仍需通过业务工具查询并校验权限。

| 细分内容 | 提供方式 |
| --- | --- |
| 现场字段 | 当前项目 ID、选中对象 ID，以及必要的类型或说明；按业务约定 |
| 对象引用 | 使用稳定编号，并说明如何通过 MCP 查询对应对象 |
| 后端证明 | 对实际提交的 context 签发现场票，绑定当前用户、企业与平台 |
| 联调样例 | 一份现场 JSON 和对应签名票，用于验证哈希与身份匹配 |

### 2.2 字段与签名方式


需要助手理解「这个项目」「选中的节点」时，企业后端需确认现场对象及用户访问权，再签署现场票。只提供页面 URL 或前端传入的对象 ID 不足以形成可信现场。

创建任务时示例：

```json
{
  "message": "修改当前选中对象的标题",
  "context": {
    "project_id": "project-001",
    "selected_object_ids": ["object-001"]
  },
  "context_assertion": "<企业后端签发的现场JWT>"
}
```

这里的 `project_id`、`selected_object_ids` 是双方约定的业务字段示例，并非中台强制的固定字段。应提供简短、稳定的对象引用与必要说明，不把整份页面或敏感数据放进现场。

现场 JWT 头部使用 `alg=RS256`、`typ=agent-scene+jwt` 和已登记 `kid`；载荷必须包含 `iss`、`aud=agent-hub-scene`、`sub`、`tenant_id`、`platform_id`、`iat`、`exp`、`ctx`。

`ctx` 是实际提交 `context` 的 SHA-256 哈希：先按键名排序生成 JSON，保留非 ASCII 字符，分隔符使用 `,` 和 `:`，不加空格，再对 UTF-8 字节计算哈希。对象字段顺序不影响哈希，数组顺序会影响。双方需提供同一上下文的序列化结果和哈希样例验证跨语言一致性；首批字段建议使用字符串、布尔值及字符串数组。

现场票的用户、企业、平台及接入连接必须与当前登录一致，有效期受同一票据时长配置限制。传入非空 `context` 时，正式票据模式要求有效的 `context_assertion`；不依赖现场的任务可以不传这两个字段。登录票不能代替现场票。

## 3. MCP Server

### 3.1 企业准备什么

企业提供可调用的业务入口，并说明首批工具如何使用。工具清单、对象 ID、返回样例及网络条件都归入这一项；可以直接使用已有接口文档补充说明。

| 细分内容 | 提供方式 |
| --- | --- |
| 服务入口 | MCP 地址、稳定 server_id、传输方式及必要的网络访问条件 |
| 首批业务工具 | 工具名、用途、参数 schema、返回结构和必要的调用依赖 |
| 结果与错误 | 成功、业务失败、权限拒绝样例；说明如何判断动作已生效 |
| 联调条件 | 可用测试环境和测试对象，以及联系人、超时、限流说明 |
| 按需补充 | 长任务查询、取消、补偿和文件访问说明；仅涉及相应业务时提供 |

如果企业目前只有 REST API，没有 MCP 服务，可先提供现有 API 文档及测试入口，由双方确定 MCP 适配层的开发分工。适配完成后再接入业务调用。


### 3.2 服务入口

当前支持 `streamable_http`、`sse`、`stdio` 三种 MCP 传输；跨企业网络接入优先约定 HTTPS 下的 `streamable_http`，最终以实际联调结果为准。企业需交付环境地址、网络白名单、TLS 条件、超时、并发和限流说明。

服务端编号 `server_id` 必须稳定，不能包含 `__`。中台内部工具标识形如 `mcp:<server_id>:<tool_name>`，由适配后实际目录确定；权限政策和异步合同必须使用匹配的工具标识。

### 3.3 工具说明

| 项目 | 企业需说明 |
| --- | --- |
| 名称与作用 | 稳定工具名，查询／创建／修改／删除什么 |
| 输入 | 字段类型、必填、取值范围、默认值；业务 ID 从哪个查询工具获取 |
| 输出 | JSON 结构、对象 ID、状态、数量、产物及结果链接字段 |
| 查询范围 | 分页、过滤条件、总量、游标；返回的是部分还是全量 |
| 权限 | 所需主体与范围，越权时如何报错 |
| 副作用 | 只读、写入、破坏性或未知；是否收费，是否可撤销 |
| 重复调用 | 是否幂等、幂等键放在哪里、有效期多久、重复参数冲突如何处理 |
| 失败 | 参数错误、权限不足、业务失败、限流、超时的错误码与执行确定性 |
| 依赖 | 哪些步骤先做，是否有并发冲突、版本号或状态前置条件 |
| 样例 | 至少一份成功、业务失败及权限拒绝回执 |

返回内容必须能区分「已执行成功」「已受理」「执行失败」「结果未知」。仅 HTTP 200 或一句「处理完成」不足以覆盖所有业务判断。长结果应支持分页或提供可继续读取的引用，减少把全部数据塞入模型上下文的需求。

若企业用一个通用工具封装所有动作，还需提供内部能力清单、内部工具名参数、参数 schema 和发现方式，由中台方配置能力发现。封装不能绕过逐工具权限和副作用约定。

### 3.4 幂等与完成判定

中台创建任务的 `Idempotency-Key` 只防止重复创建中台任务，不等于企业写操作已经获得端到端幂等保障。企业提供的幂等字段及其传递方式需逐工具联调确认。

本地文件存在用 `artifact_exists` 核对；企业平台上的查询或写入使用指向实际调用的 `tool_succeeded`，并以真实业务回执和异步终态确认结果。不能拿任意成功 MCP 回执替代本地产物，也不能把部分步骤成功说成整个目标完成。

### 3.5 异步任务（仅有长任务时）


生成视频、批处理等长任务应提交后尽快返回持久任务号，中台之后查询原任务，不重复提交。

有长任务时，在 MCP 工具说明中补充下表；没有这类业务可以跳过：

| 项目 | 交付内容 |
| --- | --- |
| 提交 | 提交工具名及受理回执样例 |
| 任务号 | 字段路径、唯一性范围、是否跨进程重启保留、可查询期限 |
| 查询 | 查询工具、任务号参数名、查询权限与限流 |
| 状态 | 全部状态词及 accepted／running／succeeded／failed／cancelled 的映射 |
| 产物 | 字段路径、文件／链接结构、访问方式及有效期 |
| 超时 | 正常耗时、最大等待时间、超时后查证方法 |
| 取消 | 是否支持、工具名、允许阶段、取消后实际效果；不支持需明确 |

以下仅展示中台配置格式，不代表企业已有这些工具。正式字段必须按实际回执修改：

```json
{
  "contracts": [
    {
      "contract_id": "enterprise-job-v1",
      "version": 1,
      "submit_tool_key": "mcp:enterprise:create_job",
      "remote_id_pointer": "/job/id",
      "status_tool_key": "mcp:enterprise:get_job",
      "status_id_argument": "job_id",
      "status_pointer": "/job/status",
      "status_map": {
        "queued": "accepted",
        "processing": "running",
        "done": "succeeded",
        "error": "failed",
        "cancelled": "cancelled"
      },
      "output_pointer": "/job/outputs",
      "recoverable": true,
      "poll_interval_seconds": 5,
      "deadline_seconds": 1800
    }
  ]
}
```

中台方通过 `ASYNC_CONTRACTS_FILE` 指定正式合同，或放到 `contracts/async_tools.json`。仓库只有 `contracts/async_tools.example.json` 示例，不会自动加载，也没有随附任何企业的正式合同。

持久任务号路径、查询工具或查询参数缺一项，即使写了 `recoverable: true`，也不能算可恢复。未知状态保持未知。查询和取消工具同样需要凭据与授权；异步开关开启不代表合同已经配置成功。

## 4. 调用凭据与授权范围

### 4.1 企业准备什么

企业提供用于调用 MCP 的凭据，并说明它代表谁、可以调用哪些工具及操作哪些对象。权限范围可以用一张表说明，中台方负责将约定落到绑定和工具政策中。

| 细分内容 | 提供方式 |
| --- | --- |
| 调用凭据 | 令牌及使用方法，通过双方约定的受控渠道交付 |
| 凭据主体 | 说明属于哪家企业、企业服务账号或哪个具体用户 |
| 工具与资源范围 | 列出允许的工具、项目／对象范围，以及直接执行、需批准或禁止的动作 |
| 凭据维护 | 有效期、轮换与撤销方式及相关联系人 |
| 数据范围 | 说明哪些业务数据可发送给模型，结果保存期限及部署要求；由双方确认落实方案 |

### 4.2 当前认证方式

当前 HTTP 适配器使用 Bearer 令牌。若企业要求自定义签名、双向 TLS、OAuth 自动刷新或其他认证流程，双方需先确认代理或适配开发，不能直接视为现有能力。

登录票与业务访问令牌用途不同。中台按企业或用户绑定读取业务凭据，当前支持 `env:变量名` 或 `file:绝对路径` 的受控引用。企业需说明令牌代表企业服务账号还是具体用户，以及资源权限如何约束。企业级服务账号不会自动继承每位员工的个人权限。

凭据明文不写入普通文档、聊天、模型提示或事件。企业通过受控渠道交付后，中台方配置受控引用、企业／用户绑定及工具政策。正式接入不共用未隔离的全局令牌。

### 4.3 权限说明示例

下表仅展示填写方式，实际角色、工具和资源范围由企业确认：

| 主体 | 允许的工具 | 资源范围 | 执行方式 |
| --- | --- | --- | --- |
| 普通成员 | 查询项目、读取对象 | 本人可访问的项目 | 直接执行 |
| 指定业务人员 | 创建或修改对象 | 已授权项目 | 按约定直接执行或逐项批准 |
| 未授权用户 | 无 | 无 | 禁止调用 |

工具和资源权限需要企业后端实际校验，不能只在文字中声明。企业级服务账号不会自动变成用户级权限；若使用服务账号，应说明如何限制其资源范围。用户登录票里的 role 不直接决定中台权限，中台方依据双方确认的映射进行配置。

登录成功证明用户身份，业务凭据与授权决定能执行哪些动作；现场签名证明当前对象信息，不能替代上述两项。


## 附录 A：双方分工


| 工作项 | 企业方负责 | 中台方负责 |
| --- | --- | --- |
| 用户身份 | 校验企业登录态，签发真实身份票，保持标识稳定 | 登记可信签发方、验签、防重放、建立中台会话 |
| 工具服务 | 暴露业务动作，返回真实结果，执行企业侧资源权限校验 | 接入工具目录、过滤授权工具、调用前核对政策与凭据 |
| 权限落地 | 确认人员、角色、资源及动作范围 | 配置中台角色／用户映射、服务端绑定、凭据绑定和工具政策 |
| 现场信息 | 后端确认项目与对象，签署现场证明 | 校验现场证明与当前登录主体一致并记录快照 |
| 异步任务 | 保持任务号可查询，提供真实状态与结果 | 配置合同、记录原任务号、由 Worker 后续查询 |
| 页面集成 | 实现企业页面入口、代理、事件消费和业务视图刷新 | 提供中台接口、过程事件、会话和任务能力 |
| 上线与运维 | 企业服务、凭据、网络和业务状态排障 | 中台部署、治理配置、执行账本、恢复和中台排障 |

企业侧仍须校验工具调用者对具体对象的权限。中台的工具授权和现场验签不能代替企业后端的对象权限检查。

## 附录 B：企业前端集成（需要内嵌助手时）


### B.1 页面与代理

建议以企业域名下的同源路径接入，例如 `/agent/api/*` 代理到中台 `/api/*`。企业方需保留 Cookie 和必要请求头，对 SSE 关闭代理缓冲，设置能覆盖业务等待的连接超时；代理路径、Cookie 路径和 HTTPS 条件必须共同验证。复用中台页面时，可用 `<body data-api-prefix="/agent/api">` 配置接口前缀。

企业可复用中台页面或自行开发助手界面。跨站 iframe 涉及第三方 Cookie，应单独验证，不能把允许跨域等同于登录态可用。

### B.2 最小接口流程

下表是中台原始路径，企业代理部署时加约定前缀：

| 步骤 | 接口 | 说明 |
| --- | --- | --- |
| 登录 | `POST /api/auth/exchange` | 用企业签发的票兑换 Cookie |
| 核对身份 | `GET /api/me` | 确认当前登录用户 |
| 创建任务 | `POST /api/tasks` | 正文含 `message`，可带 `session_id` 和现场字段；建议带 `Idempotency-Key` 请求头 |
| 查询任务 | `GET /api/tasks/{task_id}` | 读取状态和 outcome |
| 接收过程 | `GET /api/tasks/{task_id}/events` | SSE；按事件标识，通过 `after` 或 `Last-Event-ID` 补读 |
| 补充要求 | `POST /api/runs/{run_id}/inputs` | `{"request_id":"input-001","message":"补充要求"}`；重试复用同一 request_id |
| 暂停／继续／取消 | `POST /api/runs/{run_id}/pause`、`/resume`、`/cancel` | 取消不自动回滚已发生的业务动作 |
| 读取产物 | `GET /api/tasks/{task_id}/artifact` | 有本地产物时读取 |
| 退出 | `DELETE /api/auth/session` | 撤销当前中台会话 |

保存创建响应中的任务、运行和会话标识，后续分别使用接口对应的 ID，不要假定 `task_id` 与 `run_id` 相同。同一创建幂等键配不同内容返回 409。补充接口的 202 代表已收下，不代表已经改完计划或完成业务。

需要人工批准时，通过 `GET /api/runs/{run_id}/approvals` 读取清单，使用 `POST /api/approvals/{approval_id}/approve` 提交 `manifest_hash`；拒绝使用同路径 `/reject`。自建前端必须展示并确认具体动作清单，不能用一条泛化的「同意」替代。

SSE 承载过程事件，任务完成状态及 outcome 用于最终展示。企业页面中画布、列表或对象状态的刷新由企业前端根据企业后端的真实状态实现，中台不会自动操作企业页面 DOM。

## 附录 C：中台方配置与上线前核对


以下由中台方负责，企业提供相应材料配合：

1. 登记签发方、公钥、企业／平台白名单和身份源；正式环境采用 `AUTH_MODE=ticket`、`AUTH_DEV_COMPAT=false`。
2. 配置 MCP 服务地址，登记企业服务端绑定和企业级／用户级凭据引用；不得用未隔离的全局令牌替代正式绑定。
3. 根据企业确认的权限矩阵登记工具政策，配置用户或角色映射；批准方式为 `auto`、`required` 或 `never`。
4. 有异步业务时配置正式合同，核对 `/api/health` 中实际加载合同数和可恢复数，并确认 Worker 正常运行。
5. 核对数据库、结果存储目录、网络、Cookie、可信来源和事件流。正式票模式自动启用工具政策、结果信封和异步运行三项，但仍需验证每项实际配置。
6. 按企业的数据范围及保留要求确认部署方案，记录哪些内容会传给模型、哪些结果落盘，以及清理与访问方式。未实现的要求先明确差距，再决定接入范围。

当前版本的边界需在项目启动时说明：规划失败不会生成固定业务计划；完整模型调用的上下文预算治理尚未完成；并发上限为单进程上限；没有持久任务查询合同不能承诺异步恢复；没有适配好的远端幂等机制不能承诺外部写入恰好一次。需据此约定工具目录规模、结果分页和首批业务范围。

## 附录 D：联调与验收


| 验收项 | 操作 | 通过标准 |
| --- | --- | --- |
| 身份 | 正常票、过期票、错误签名、重复兑换 | 正常登录；无效票拒绝；已消费票返回冲突 |
| 企业隔离 | 使用甲企业身份访问乙企业任务、结果及业务对象 | 中台和企业服务均拒绝越权，无业务副作用 |
| 用户隔离 | 同企业两个用户读取彼此私有任务或对象 | 按约定权限拒绝，服务账号不造成意外权限扩大 |
| 工具授权 | 未授权工具、已撤销凭据、需批准动作 | 未放行前不发送业务调用；批准与具体清单一致 |
| 现场 | 修改 context、替换用户或平台、使用过期现场票 | 拒绝不匹配的现场，不对错误对象执行 |
| 业务成功 | 执行一个完整首批场景 | 企业后端对象实际符合预期；中台结果与其一致 |
| 业务失败 | 模拟参数错误、权限不足、业务拒绝 | 返回可理解失败原因，不误报成功 |
| 幂等 | 重发创建请求；对写工具按约定重复发送 | 中台只建一次；企业写入满足双方约定的幂等行为 |
| 不确定结果 | 模拟发送后连接断开 | 不盲目重复写入，能查询查证或进入待核实 |
| 异步恢复 | 提交长任务后重启中台执行进程 | 原任务号继续查询，不重新提交；最终结果一致 |
| 取消／补偿 | 取消运行并检查企业状态 | 准确区分停止调度、远端取消和业务撤销 |
| 前端断线 | 断开事件流后重连 | 能补读过程并取得最终状态，不重复创建任务 |
| 产物 | 下载文件并检查访问限制与过期行为 | 文件可用、归属正确、链接及保存期限符合约定 |
| 限流／容量 | 按约定压力发起任务 | 不越过双方限制；排队、失败或重试行为可解释 |

现场、异步、产物等用例只对已启用的能力执行。测试需要的第二企业、受限用户和故障情形可由沙箱或测试替身提供，但正式入口仍需验证真实认证、权限及网络配置。

联调顺序：材料确认 → 网络与工具直连 → 登录与隔离 → 单工具 → 完整业务 → 异步／恢复／故障 → 企业前端 → 小范围上线。每阶段记录通过项、未通过项、责任人和修复时间。
