# 工具结果驱动的观察与决策循环：详细实施方案

日期：2026-10-23。状态：设计方案，未修改执行代码、未运行验收。基于本次读取的当前工作区，现有未提交实现应予保留。

## 1. 当前差距已经缩小，但缺少结果驱动的决策

当前 `app/graph.py` 已有 intake、plan、persist_plan、revise_plan、run_step、finalize；不是早先只有 plan/run_step 的版本。

`nodes.revise_plan()` 明确只处理“补充导致的剩余部分调整”；`next_step()` 在 intent_changed 时修订，否则继续步骤或收尾。它还没有通用的工具结果观察入口。

本轮应增加：用户要求不变时，系统也能根据已读取的新事实判断继续、替换剩余步骤、补查、等待、核实或结束。例如先列出真实素材，再挑选片段，而不是第一份计划就猜素材 ID 和剪辑点。

保留两类路径：

- 直接参数绑定、步骤确定：连续执行，不增加模型观察请求。
- 选择、判断、异常调整依赖实际结果：到明确边界才返回模型。

不切换 Pi，不重建账本，不改变 MCP 为主要业务调用通道；首版仍顺序执行。

## 2. 必须保持的约束

1. 每次外部调用仍经过现有租约、用户要求版本、权限、动作账本和参数校验。
2. 观察模型不直接执行工具，也不能修改账本、授权、租约或已完成事实。
3. 已成功操作不能因为新计划版本重复执行；结果未知先核实，不能当失败重发。
4. 新用户输入优先于旧要求的自主调整；模型请求过程中到达的新要求使旧候选失效。
5. 计划完成只是步骤执行结束，任务完成要另外核对可验证条件。
6. 自主观察、计划修复、结构化解析重试和用户补充修订共用运行级预算。
7. 模型实际没读取媒体内容时，不能凭素材名称或元数据认定“画面适合、台词正确、质量合格”。

## 3. 先把目标、当前执行片段、完成条件分开

### 3.1 不再要求首次计划包含未知的全部步骤

任务目标保持稳定，例如“选三个合适片段制作短片”。首次只提交可确定的片段，例如：

```json
{
  "summary": "先查清当前可用素材",
  "steps": [
    {
      "step_id": "p1_s1",
      "tool": "实际发现的素材清单工具",
      "args": {"project_id": "已经核实的项目引用"},
      "why": "取得真实素材身份、类型和可用状态"
    }
  ],
  "after_segment": "observe",
  "observation_goal": "根据真实清单决定还需要读取哪些素材内容与时长"
}
```

以上工具和参数只是合同示意，实施必须使用真实目录与 schema。不能把示例名称硬编码进内核。

对确定的“读取已知产物 → 打包 → 导出”，可以提交多个步骤并令 after_segment=verify；直接 ref 能解决的数据依赖不需要模型。

### 3.2 Schema 变化

在 `ExecutionPlan/RevisedPlan` 或统一的候选计划结构中增加：

- `after_segment`: observe / verify。
- `observation_goal`: 下一次需要判断什么，observe 时必填。
- `completion_criteria`: 本任务的可验证要求与需模型评价的要求，分开记录。

首版先做“片段结束观察”；无需同时实现每步任意 checkpoint。以后确有需要，再支持显式 observe_after，但不能与片段结束重复触发。

首次 plan 可要求至少一个实际步骤。观察后的结束/等待是独立决策，不靠提交空工具计划表示。没有真实工具步骤的 continue 属于无效决策，避免空转。

完成条件变化必须能追溯到用户新要求；自主观察不能为了方便删掉目标中“要三个片段”“需要声音”等条件。

## 4. 增加程序观察层，先判断是否值得调用模型

建议新增 `app/observation.py`，纯函数和合同为主，分开“程序采集事实”与“模型解释事实”。

### 第一步：每个工具保存统一结果

在现有 runner 与 step 输出外形成明确结果合同：

```text
ToolResult:
  action_id / attempt_id / step_id / tool_key
  execution_status: succeeded / failed / unknown
  phase: accepted / processing / completed / materialized（工具支持时）
  data_ref: 完整原始结果的授权引用
  summary: 给模型看的有界摘要
  artifact_refs / external_receipt_refs
  evidence_refs: 与资源版本和读取范围关联
  complete / next_read_ref: 是否全量及如何继续读取
  error: code / phase / execution_certainty
```

它是平台归一结果，不要求所有 MCP 服务端原生返回同一 schema；缺失字段保持未知，不能由模型补成事实。

当前 `tool_results_text()` 直接按字符截断，适合简短回答但不够支持观察：新增结果存储与有界读取入口，保留完整 JSON、文本和可用内容块。嵌套数组、素材清单、任务 ID 与回执不能只剩几个标量；大结果落产物或结果存储，用受控引用读取，禁止任意本地路径。

### 第二步：确定性检查器

新增 `collect_observation()` 与 `route_after_step()`，依据真实结果、计划片段策略和控制状态输出路由：

| 观察情形 | 路由 | 是否调用模型 |
| --- | --- | --- |
| 要求版本变化 | 用户输入修订 | 是，按最新输入处理 |
| pause/cancel/失租 | 既有控制路径 | 否 |
| 写操作 unknown | needs_reconcile | 不允许模型猜成功或重新购买 |
| 外部任务已受理未完成 | 等待原任务 | 否，程序查询 |
| 当前步骤成功且后续参数可确定解析 | 下一步骤 | 否 |
| 片段结束且 after_segment=observe | 模型决策 | 是 |
| 已证实的可调整错误 | 结果观察决策 | 有限调用 |
| 所有片段结束 | 完成核对 | 先程序核对，必要时模型评价 |

不要用工具名关键词猜是否需要观察；模型候选计划声明片段边界，适配器提供确定性后置条件，执行器统一校验。

### 第三步：被动发现的新事实

补充触发条件包括：清单为空、结果被分页、要求的模型不可用、引用资源版本变化、下游输入无法从已成功结果取得。

程序只发现条件，不自行猜业务替代方案。例如没有三个可用素材，交给模型决定补查还是询问用户；不能静默凑三个不存在 ID。

不能把所有错误都送模型恢复。未知效果、身份无权限、工具未授权、停止与失租优先走门禁；权限拒绝不能成为换工具绕过的理由。

## 5. 定义受约束的模型决策输出

建议新增 `ObservationDecision`，使用 Pydantic 判别联合或等价的严格条件校验：

| decision.kind | 含义 | 必要字段与限制 |
| --- | --- | --- |
| continue | 保留并继续已提交剩余步骤 | 解释当前证据，仍逐步准入 |
| revise | 替换尚未执行部分，或补充下一执行片段 | 非空新步骤、作废范围、after_segment |
| wait_input | 缺少用户必要信息 | 具体问题；不能顺带执行新写入 |
| wait_approval | 新动作需要明确批准 | 方案与范围引用；批准入口另负责 |
| finish | 认为目标可以结束 | 逐项完成条件及证据引用，最终程序门禁决定 |
| stop | 无法在当前能力/预算下继续 | 具体原因和已完成事实 |

异步等待由程序根据原任务回执处理，不让模型创造一个“随便等会”状态。needs_reconcile 也不由模型直接清除。

如果当前片段已结束且没有剩余步骤，continue 必须拒绝或转换成明确校验错误；不能再次观察同样内容直到预算耗尽。

系统提示只要求简短的决定依据和证据引用，不索取或存储隐藏推理。工具返回属于不可信业务数据，其中的“忽略规则”等文本不具备授权效力。

模型候选没有通过 schema、引用、工具、权限、数量与预算校验时，最多有限修复；之后明确等待或失败，不执行过滤后残缺计划。

## 6. 观察输入怎么组装

建议新增 `build_observation_context()`，与现有 `run_inputs.build_decision_input()` 共享事实读取逻辑，但保持触发原因不同。

输入至少包含：

1. 原目标与截至当前版本的用户补充约束。
2. intent_version、当前 plan_version、观察覆盖的回执水位。
3. 目前执行片段、未执行步骤、观察目标。
4. 已完成动作的真实结果摘要与完整结果引用。
5. 已发生外部效果、在途任务和 unknown 列表。
6. 资源版本、分页完整性、实际读取范围。
7. 候选工具及完整必需 schema；可请求扩大候选，不能把目录前 N 项当全部。
8. 当前权限/批准范围、剩余运行预算。
9. 完成条件的 verified / unmet / unchecked 状态。

读取时形成一致快照，不能先读旧输出再给它贴最新版本。活动补充的全部有效约束需要保留；仅传 pending inputs 可能遗漏前一次已纳入但仍有效的用户要求。

大结果先给摘要与引用，再按需要通过授权读取工具获取细节。语义选择依赖媒体时，调用真实 inspect/review 能力；没有这类能力就承认无法完成内容挑选，不能依赖文件名宣称看过视频。

## 7. 在现有图上增量接入

建议增加 `observe_result`、`decide_next`、`verify_completion` 三个节点：

```text
intake → plan → persist_plan → run_step → observe_result
observe_result → run_step                 确定步骤继续
observe_result → revise_plan              用户新要求
observe_result → decide_next              需要结果判断
observe_result → wait/stop                控制、未知或异步等待
decide_next → run_step                    保留剩余计划
decide_next → persist_plan                新片段或修订候选
decide_next → wait/stop                   缺输入、批准或无法继续
decide_next → verify_completion           提出完成
verify_completion → decide_next           条件未满足且可有限修复
verify_completion → finalize             程序核对通过或明确部分结局
```

observe_result 是便宜的程序判断，不默认调用 LLM；decide_next 才是模型调用。每个工具之后都可以跑程序观察，只有需要语义判断才付出模型请求。

用户补充修订与结果自主决策可共用候选计划校验/提交服务，但不要通过伪造 intent_changed 强行复用 `revise_plan()`：没有新输入时 intent_version 不变，只有 plan_version 增加。

新增 `revision_reason`: user_input / observation / recovery_repair；分别记录计数，同时共享总预算。当前用 plan_version - 1 推导用户修订次数的逻辑需要调整，自主片段也会增加计划版本。

## 8. 接续计划、动作身份与参数绑定

1. 新片段只包含接下来需要实际执行的步骤，给出 run 内唯一 ID。
2. 旧已执行操作与输出永久保留，新计划显式引用可信历史 step/action/产物。
3. 旧未执行步骤可保留或标 superseded，决策不能篡改其真实执行状态。
4. 计划提交仍比较租约、intent_version 和 base_plan_version；观察水位也纳入准入条件。
5. 候选已经过时就重新读取，不把最新数据默默套到旧候选。
6. 新计划中再次调用已完成外部效果，必须有明确的新业务意图和授权；不因计划版本变化自动重做。
7. 参数生成分两类：直接 ref 按受限 JSON Pointer 解析；“挑三个”“总结后写标题”等语义转换由模型基于真实结果输出。
8. 禁止让 JSON Pointer 变成任意 Python、eval 或模板表达式；不增加隐式文件读取。

`validate_plan` 需接收可信历史输出集合，正确校验对成功旧步骤的引用和依赖。外部 ref 必须指向本 run 或显式授权的产物，不允许模型伪造“已完成”对象。

## 9. 观察记录、版本水位与崩溃恢复

建议新增持久 `run_decisions`，至少保存：

```text
decision_id / run_id / reason / status
intent_version / base_plan_version / observation_seq
input_snapshot_ref / result_snapshot_ref
candidate_plan_hash / committed_plan_version
model / request_count / usage / timestamps
```

observation_seq 为运行内单调水位：每次相关步骤/任务结果落库时在同事务推进。不能用墙钟时间判断新旧。外部资源版本仍独立校验，此水位不代表对外部系统做了完整快照。

流程：先事务预留决策与预算、保存输入快照引用 → 调模型 → 校验 → 按租约/要求/基计划/水位 CAS 提交决策和新计划或结束建议。每次 provider 实际请求都计数；解析重试也是新请求。

同一观察触发的执行用稳定决策身份去重；若需要读取更多结果，水位/输入快照变化后产生新决策。相同输入下再次请求模型必须计为显式重试，不能通过换 decision_id 绕过预算。

崩溃语义：

- 模型未请求：可继续预留记录。
- 请求已发、未落响应：计为已消耗请求；不能宣称供应商没计费。按有限恢复策略处理。
- 候选已保存、未提交：若版本仍匹配可校验提交，否则废弃。
- 计划已提交、响应丢失：读回原提交，不多建版本，不重复动作。
- 工具完成、观察未开始：从回执与快照进入观察，不重新执行工具。

快照保存 next_route、当前片段策略、未消费观察水位、决策引用和累计预算。恢复入口同时判断待处理输入与待观察结果；不再仅以“计划步骤跑完”直接收尾。

## 10. 错误处理、异步等待与补偿

当前 run_step 在确定失败后可能直接补偿并停止。要在异常分类后分支：

| 情况 | 本轮处理 |
| --- | --- |
| 本地缺参/资源版本冲突，确认未发生外部效果 | 保存错误事实，可有限观察修正 |
| 远端确定拒绝且合同允许修复 | 保存回执，模型决定换参数/询问/结束；仍检查授权 |
| 已发送后断连接、解析失败、结果 unknown | needs_reconcile，不模型重发 |
| 权限拒绝、停止、失租 | 既有控制路径，不让模型绕过 |
| 外部任务 accepted/processing | 查询同一个 task，不让 LLM 轮询 |

失败恢复前不能先无条件执行补偿：否则模型观察到的是已被撤销的状态，无法继续原工作。为步骤明确 failure_policy，优先保留结果并进入观察；真正选择终止且合同明确允许时，才按显式补偿策略执行。unknown 永不自动补偿。

首版可只对查询成功结果和本地未执行错误开启观察，对确定写失败保持现有停止策略，降低首次改造范围。

异步适配器需要提供原任务查询与完成条件。服务端没有这些能力时明确等待/人工核实，不假装平台有通用后台接续。任务受理、执行完成、产物保存是不同阶段。

## 11. 完成核对与避免提前结束

新增程序验证器，输出每条 criterion 的 verified、unmet、unchecked 及证据引用。确定性条件来自能力适配器与真实回执，不能执行模型生成的任意断言代码。

例如：产物是否存在、是否绑定、实际时长/规格是否符合、工程导出回执是否成功，均可程序核对；镜头内容是否合适需实际内容读取和有限模型评价。文件存在不代表画面质量满足要求。

观察模型提出 finish 后必须经过 verify_completion 和现有最终事务门禁。缺少检查证据时不能宣称全面完成；需要额外收费的修复仍走批准。

如果所有确定条件满足且任务不要求语义验收，可直接程序结束，避免多一次“恭喜完成”的 LLM 调用。

系统发现计划仍有未完成条件时，最多有限继续，不强制无限自主补做。预算不足时报告已完成、未完成和未检查部分，保留可恢复状态。

## 12. 预算与无进展保护

基于 runs 的 budget/consumed 持久化累计，而不是仅在 state.usage 显示统计。建议设置以下可配置项，具体初值由假服务和真实小样测定：

- 最大 provider 请求数，包含初始规划、观察、用户修订、结构化修复和最终回答。
- 最大自主决策次数及最大连续无进展次数。
- 最大实际工具调用数与外部写操作数。
- 运行总时长与异步等待期限，二者单独定义。
- 输入/输出 token 上限；人民币硬上限只有具备可靠报价与结算合同时才承诺。

预算在发请求前原子预留，返回后记录实际用量；不能靠只统计成功返回来漏掉超时请求。`structured_call(attempts=2)` 的内部重试也需计入，放在 provider 调用层统一处理。

无进展指纹包括 intent、已知结果水位、完成条件、拟执行工具与最终参数。相同查询在同一资源版本反复执行、同一失败参数重复出现、连续决定继续却无步骤，应阻断或要求澄清。不要仅按文字摘要判断进展，也不要禁止用户明确要求的重复生成。

| `app/persistence.py` / `app/pg_store.py` | decision 存储、预算预留、结果水位、CAS 提交与恢复读取 |
| `app/ledger.py` | 完整回执引用和原动作身份保持；版本变化不重复效果 |
| `app/services.py` | 所有 provider 尝试的统一预算与用量记录 |
| `app/main.py` / `app/api_hub.py` | 恢复下一路由、计数和持久决策，不因重启重置预算 |
| `app/config.py` / `.env.example` | 观察开关与预算配置，明确试验初值 |
| `app/events.py` / 前端 | 观察到新结果、调整后续、等待核实等事件与耗时，不展示内部推理 |

## 14. 按六个阶段实施

### 阶段 A：只引入观察事实，不自动改计划

增加 ToolResult、结果完整引用和程序 observe_result；固定计划仍照旧。验证小结果、嵌套数组、大文本、分页和未知回执能完整追溯。功能开关保持关闭。

### 阶段 B：片段式规划

增加 after_segment/observation_goal。规划器允许“先查再定”，执行片段结束先进入明确等待或记录观察；不因有文件就成功。给简单确定任务保留 verify 快路径。

### 阶段 C：接入模型 decide_next

先只支持 revise、wait_input、stop；复用候选校验和 CAS 提交，验证历史输出引用。随后支持 continue、wait_approval 和 finish。每种分支都需对应测试，不先做一个自由文本反思工具。

### 阶段 D：恢复与预算

持久 decision/水位/预算，接入新输入抢占候选和进程恢复；内部结构化重试纳入计数。完成前不对外默认启用。

### 阶段 E：完成验证与有限错误修复

接入 criterion 验证器；逐项开放确定错误的有限修复；补偿策略改为显式终止后的决定。异步等待仅对具备合同的工具开放。

### 阶段 F：前端与灰度验收

显示“正在根据结果决定下一步”，明确用户无需补一句“继续”；确定步骤仍直接运行。先在测试能力包开启，再逐能力开放，关闭开关时已有待观察任务需安全暂停或继续由兼容执行者处理，不能跳过观察边界。

## 15. 验收用例

1. **确定链路**：读取已知产物、打包、导出；观察模型请求数为零。
2. **未知清单**：初始模型只能列素材，拿到真实返回后再挑选；初次计划无虚构 ID。
3. **语义选择**：只给元数据时必须补查实际内容或声明能力不足，不能声称已看媒体。
4. **空清单**：有限补查或询问，不硬凑三个片段。
5. **大清单分页**：完整性未知时不宣称已比较所有候选，读取尾页可发现目标。
6. **直接 ref**：前一步返回 ID，下一步只是确定绑定，不额外调用模型。
7. **本地未执行错误**：可修复参数，但不绕过 schema 和授权。
8. **远端已写后断连**：needs_reconcile，模型不得重复写入。
9. **新输入竞争**：观察模型返回时用户要求已变，旧候选不提交。
10. **已完成效果复用**：增加计划版本不增加已成功远端写入计数。
11. **受理后等待**：轮询原任务不增加 LLM 请求，不重新受理。
12. **提前 finish**：缺产物/绑定/导出回执或必要证据时不能成功。
13. **无进展循环**：重复查询/空 continue 在预算内停止。
14. **预算耗尽**：保存已完成事实与待观察点，恢复不归零。
15. **崩溃窗口**：工具成功后杀进程，重启进入观察而不重跑工具；计划提交后重启不重复决策提交。
16. **暂停/取消/失租**：观察和模型等待期间也遵守既有控制合同。
17. **确定失败补偿**：有限修复前不无条件撤销既有成功步骤；选择结束后才执行被授权补偿。
18. **最终竞争**：验证通过后又有新输入，最终事务仍能拒绝旧完成结果。

测试采用一次性 PostgreSQL、本地受控模型和 MCP，assert 实际模型请求数、远端工具调用次数、动作身份和数据库版本。并发通过 barrier 控制；需要独立进程真实恢复。原工作区存在其它实现变更，施工时按当前文件增量修改，不重置未提交内容。

## 16. 最小落地示例

用户要求“从项目素材里挑三个适合的片段，剪一个短片”。

1. plan 只提交已授权项目的素材查询片段，after_segment=observe。
2. 执行器取得真实素材列表、保存完整结果及水位，程序判断需要语义选择。
3. decide_next 看见真实 ID 与未检查状态，提交读取候选时长和内容的片段。
4. 程序连续执行相互独立的读取；有真实内容后，再调用一次模型选择三个片段并形成剪辑参数。
5. 校验器核实 ID、区间和授权，提交剪辑/导出的确定步骤，程序连续执行。
6. 验证输出真实存在、规格和导出回执；用户要求内容质量时，按实际可用证据检查。
7. 全部必需条件有依据后，通过最终门禁交付；若工具不足或证据缺失，如实等待或报告限制。

首轮实现成功的标志是：用户不必补发“继续”才能触发结果判断，模型不必提前猜未知参数，程序确定步骤也没有被每步观察拖慢。
